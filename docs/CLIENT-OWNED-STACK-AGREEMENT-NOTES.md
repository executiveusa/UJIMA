# Client-Owned Stack — Agreement Notes

**Type:** Internal operator reference / attorney review aid  
**Status:** Gate 5A — ready for Architect review before client use  
**Important:** This is not legal advice and not a final contract. Use for operational planning and attorney review only. Attorney/client contract review required before use as a binding agreement.

---

## Purpose of this document

This document records the intended ownership model for Mission OS deployments, the key operational terms Asc3nd applies consistently, and the areas that require attorney drafting before they become enforceable agreements.

This is not a contract. It is a working model for attorney review.

---

## Core ownership principle

The client owns the deployed Mission OS stack. This includes:

| Asset | Ownership after handoff | Notes |
|---|---|---|
| VPS or server | Client | Client provisions and pays for VPS directly |
| Source code | Client (MIT License) | MIT license — full ownership, no royalties, no restrictions |
| Database (SQLite or Postgres) | Client | Stored on client's VPS; all backups belong to client |
| All data in the database | Client | Tenant data, event journal, artifact registry, approval records |
| API keys and credentials | Client | Generated by client; Asc3nd never stores client API keys |
| Hermes agent runtime config | Client | Config files stored on client's VPS |
| ICM workspace and all outputs | Client | Stage contracts, artifacts, approvals — all on client's VPS |
| Domain and DNS | Client | Client registers and controls domain |
| Backup archives | Client | Stored on client's VPS or backup destination of client's choice |

After handoff, Asc3nd has zero access to the client's server unless the client grants continued access for optional maintenance or managed-agent support.

## MIT license — what it means for the client

The Mission OS source code is released under the MIT License. Key implications:

- The client may use, copy, modify, merge, publish, distribute, sublicense, and/or sell copies of the software
- The client is not required to pay Asc3nd royalties or licensing fees
- The client may hire any other developer to maintain or modify the system
- The client is not locked into Asc3nd for any future work
- Attribution: the MIT license notice must be retained in source distributions — this is a standard open-source requirement, not a business restriction

The MIT License text is included in the repository at `LICENSE`.

## What Asc3nd is in this relationship

Asc3nd is an implementation partner, not a software licensor or SaaS provider.

Asc3nd's role is to:
1. Configure and deploy the client's Mission OS installation
2. Train staff
3. Hand off full control to the client
4. Optionally provide ongoing maintenance or managed-agent support if contracted separately

Asc3nd is not:
- A landlord of the software
- A data processor (no client data is processed on Asc3nd infrastructure post-handoff)
- A compliance officer, legal advisor, or auditor
- A guarantor of AI output quality or grant funding outcomes

---

## Access termination at handoff

At handoff, Asc3nd will:
- Transfer all credentials generated during deployment
- Revoke any SSH keys used during deployment (or confirm to client which keys remain, if ongoing support is contracted)
- Provide the client with the full operator manual and all runbooks
- Remove or archive any Asc3nd-specific deployment records

If the client purchases optional maintenance or managed-agent support, Asc3nd retains SSH access only for the duration of that contract, using a dedicated key pair agreed at setup. The client retains the ability to revoke this access at any time.

## Data handling notes (for attorney review)

These are operational facts, not legal representations:

1. **During deployment:** Asc3nd operators may temporarily access the client's VPS via SSH to perform setup. No client data is copied to Asc3nd systems.
2. **After handoff:** Asc3nd has no access to client data unless the client grants it for support purposes.
3. **No cloud sync:** Mission OS does not sync client data to Asc3nd servers, analytics platforms, or third-party services.
4. **LiteLLM routing:** When the client uses AI model APIs (OpenAI, Anthropic, Google), data is sent from the client's VPS directly to the model provider under the client's API key and the model provider's terms of service. Asc3nd is not in that data path after deployment.
5. **Langfuse:** If the client uses self-hosted Langfuse (included in standard deployment), trace data stays on their VPS. If the client separately configures a Langfuse cloud account, that is the client's relationship with Langfuse.

**Attorney note:** A formal data processing agreement (DPA) between Asc3nd and the client may be appropriate depending on the client's regulatory context. This document does not constitute a DPA.

## What Asc3nd does not guarantee

These exclusions should be reflected in any formal contract:

- **No grant outcome guarantees.** Mission OS agents draft grant-related content for human review. Asc3nd does not guarantee funding decisions.
- **No donation outcome guarantees.** Communications drafted by agents are reviewed by staff. Asc3nd does not guarantee donor responses.
- **No legal compliance certification.** Mission OS is not certified for HIPAA, FERPA, COPPA, or other regulated frameworks. Organizations with compliance obligations should consult qualified legal counsel before deployment.
- **No AI output quality guarantee.** Agents produce drafts for human review. Output quality depends on knowledge base quality, prompt configuration, and model provider capability.
- **No uptime SLA** (unless separately contracted). Mission OS runs on the client's VPS; uptime depends on the VPS provider and client infrastructure.

## Areas requiring attorney drafting

These areas are not covered by this document and require formal legal work:

1. **Service agreement / statement of work** — The formal contract between Asc3nd and the client for the one-time setup engagement, defining scope, payment terms, deliverables, and acceptance criteria.
2. **Maintenance agreement** — If the client purchases ongoing maintenance, a separate agreement defining scope, SLA (if any), access terms, and termination should be drafted.
3. **Data processing agreement** — If the client is subject to privacy regulations (GDPR, CCPA, state equivalents), a DPA may be required.
4. **Liability limitation** — Standard service agreement language limiting Asc3nd's liability for AI output errors, system failures, or data issues.
5. **Confidentiality / NDA** — If the client's data includes sensitive program or client information, mutual confidentiality terms during deployment.
6. **Dispute resolution** — Jurisdiction, governing law, dispute resolution process.
