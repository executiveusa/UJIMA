# Managed Agents as a Service — Mission OS v0.6

**Audience:** Technical operators, implementation staff, Architect  
**Purpose:** Define what "managed agents" means in Mission OS, what the service boundary is, and what is live vs. deferred  
**What is not here:** Claims of autonomous agent execution, live model routing, or live external integrations  
**Gate 5A:** Client-facing managed-agent support definition at `docs/MANAGED-AGENT-SUPPORT-PACKAGE.md`. Offer package index at `docs/SOVEREIGN-AI-OFFER-PACKAGE.md`.

---

## What "managed agents" means in this system

Mission OS provides a managed agent runtime layer. "Managed" means:

1. Agents are configured and provisioned by the operator (not self-spawning)
2. Every agent action that touches the outside world requires a human-approved approval record
3. Agent state is tracked in Mission OS as the system of record (not inside the agent runtime)
4. Agent spending is tracked in the model usage ledger
5. Agent outputs are registered as artifacts with audit trail
6. Agents are isolated per tenant (no cross-tenant execution or data access)

---

## The managed Hermes bundle

Hermes is the agent runtime Mission OS provisions and supervises. Each tenant gets a Hermes configuration bundle:

```
handoff/<slug>/managed/hermes/env        — Hermes environment (gitignored)
handoff/<slug>/managed/hermes/SOUL.md    — Agent identity definition
handoff/<slug>/managed/hermes/MEMORY.md  — Runtime state definition
handoff/<slug>/managed/hermes/USER.md    — Staff context
handoff/<slug>/managed/hermes/skills/    — 8 skill definitions
```

The bundle is generated by `missionctl hermes provision <slug>` and `missionctl bundle up <slug> --dry-run`. Generated env files contain credentials and are gitignored — they are never tracked in version control.

## Operator dashboard

Staff access the ops dashboard at `/ops`. It provides:

- **Overview:** tenant health, recent events, system status
- **Agents:** provisioned managed agents, health status per agent
- **Artifacts:** outputs registered by agents (documents, manifests, exports)
- **Events:** typed audit event feed (MODEL.CALL, AGENT.RUN, APPROVAL.CREATED, etc.)
- **Budgets:** model usage by surface, cost, and token counts; spend vs. budget bar
- **Deployments:** release lifecycle, upgrade/rollback state, backup history
- **Health:** system health check (doctor output)

The dashboard reads from `@asc3nd/core` modules directly via a same-origin server-side proxy. No operator key is exposed to browser JavaScript.

## Dry-run safety defaults

All Phase 7 and Phase 8 control plane operations run in dry-run mode unless a live VPS with real credentials is configured. Dry-run means:

- `missionctl bundle up <slug> --dry-run` — generates local config files without deploying
- `missionctl bundle smoke <slug> --dry-run` — runs 70 static checks without touching live systems
- `missionctl bundle upgrade <slug> --dry-run` — validates migration path without executing
- `missionctl bundle rollback <slug> --dry-run` — validates rollback target without executing
- `missionctl backup create <slug>` — creates local backup archive (no remote upload)
- `missionctl backup restore <slug> <id>` — restores from local archive with path-traversal guard

No live Docker, VPS, DNS, or external API calls are made in dry-run mode.

## Human approvals (non-negotiable)

Every external action requires a human-approved approval record before execution. The approval policy is:

| Risk class | Examples | Required |
|---|---|---|
| Green | Internal read, summary, analysis | Automatic (no approval) |
| Yellow | Draft creation, recommendation | Operator review recommended |
| Orange | External communication, publishing, sponsor/donor contact, browser action | Human approval required |
| Red | Money, legal/compliance, youth records, grant submission, sensitive data | Human approval required + documented rationale |

Orange and red actions cannot execute without an approval record in `APPROVED` state. The approval lifecycle enforces this at the core module level.

## Tenant packs

Each tenant gets an agent pack manifest that defines:

- Tenant identity (slug, org name, domain, timezone)
- Agent roles and skill assignments
- Approval policies per action type
- LiteLLM model routing preferences
- Langfuse project and trace configuration

Agent packs are generated by `missionctl pack generate <slug>` and stored in `mission-data/<slug>/tenant-agent-pack/`. They are not secrets and can be tracked if they contain no credentials.

## LiteLLM / Open WebUI / Langfuse config contracts

These three services have config contract files generated by missionctl:

| Config | Generated at | Format | Contains credentials? |
|---|---|---|---|
| `handoff/<slug>/managed/litellm/config.yaml` | `bundle up` | YAML | No (key injected at deploy time) |
| `handoff/<slug>/managed/open-webui/env` | `bundle up` | env | Yes (gitignored) |
| `handoff/<slug>/managed/langfuse/env` | `bundle up` | env | Yes (gitignored) |

LiteLLM config defines model routing (which models are available, fallback order, budget limits). Open WebUI env defines the per-tenant workspace. Langfuse env defines project, public key, and secret key (populated at deploy time from operator-generated credentials).

## Backup and restore lifecycle

```
create:  missionctl backup create <slug>     → backups/<slug>-<timestamp>-<rand>.tar.gz
list:    missionctl backup list <slug>        → shows all backups for tenant
restore: missionctl backup restore <slug> <id>
```

Restore validates:
- Backup ID matches tenant slug (no cross-tenant restore)
- Path traversal guard (no `../` or absolute paths in backup ID)
- Archive exists and is readable

Backups are local-only in Phase 8. Remote backup storage (S3, Hostinger object storage) is deferred to production deployment.

## Monthly support model

The managed agents service is a recurring relationship, not a one-time deployment. Monthly support includes:

- Reviewing approval queue for blocked items
- Updating agent skill definitions as workflows evolve
- Monitoring model budget consumption
- Applying Mission OS updates (new phases)
- Backup verification drill
- Security gate re-runs after any infrastructure change

---

## What this service is not

- Not a SaaS platform with a shared backend (single-tenant per VPS by default)
- Not autonomous (every external action requires human approval)
- Not a grant writer (assists with drafts; submission is always human-approved)
- Not a social media manager (publishes only after explicit staff approval)
- Not a donor outreach system (initiates contact only after explicit staff approval)
- Not a legal or compliance system (never files, never submits, never executes without approval)
