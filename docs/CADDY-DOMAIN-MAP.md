# Caddy Domain Map — Mission OS Phase 9 Staging

**Audience:** Operator configuring the reverse proxy for a Hostinger VPS staging deployment
**Purpose:** Document public vs. protected routes, TLS behavior, and how to safely replace the demo `Caddyfile.managed` placeholders

---

## Domain model recap

```
os.<client-domain>       public candidate — Mission OS web app
api.<client-domain>      public candidate — Mission API
agents.<client-domain>   protected/internal — Hermes
traces.<client-domain>   protected/internal — Langfuse
models.<client-domain>   protected/internal — LiteLLM
```

Only `os.<client-domain>` and `api.<client-domain>` are candidates for public DNS. `agents`, `traces`, and `models` must remain protected unless an explicit access-control layer is configured (SSH tunnel, VPN, IP allowlist, or an authenticated Caddy route with `basic_auth` / forward-auth). No real client domains appear in this document.

## Public routes

| Route | Upstream | Notes |
|---|---|---|
| `os.<client-domain>` | `site:3000` | Mission OS public site + `/ops` dashboard. `/ops/*` still requires session login — public DNS exposure does not bypass application-level auth. |
| `api.<client-domain>` | `mission-api:4000` | Mission API. Operator API routes (`/api/operator/*`) and Agent Service API routes (`/api/agent/*`) require a Bearer operator key regardless of network exposure. |

## Protected routes

| Route | Upstream | Access method |
|---|---|---|
| `agents.<client-domain>` (or unmapped) | `hermes:8765` | Not routed through public Caddy by default. Access via SSH tunnel (`ssh -L 8765:127.0.0.1:8765 deploy@<vps-ip>`) or an internal-only VPN. If a subdomain is configured, it must sit behind `basic_auth` or forward-auth in the Caddyfile — never expose without an auth layer. |
| `traces.<client-domain>` (or unmapped) | `langfuse-web:3000` | Same pattern as `agents.<client-domain>` — SSH tunnel or authenticated route only. |
| `models.<client-domain>` (or unmapped) | `litellm:4000` | LiteLLM has no public port in the default managed bundle (`handoff/<tenant>/managed/docker-compose.managed.yml`). It is reached only by Hermes and Open WebUI over the Docker internal network. |

## Internal-only routes (no subdomain, no public path)

| Service | Bind address | Reason |
|---|---|---|
| Hermes dashboard | `127.0.0.1:8765` | Managed agent runtime — never exposed publicly per `docs/HERMES-MISSION-OS-CONTRACT.md` |
| Grafana | `127.0.0.1:3002` | Operator-only metrics view |
| Prometheus | `127.0.0.1:9090` | Operator-only metrics scrape endpoint |
| Postgres | Docker internal network only | No host port binding in the managed compose file |

These bind addresses match `handoff/demo-pnw/managed/docker-compose.managed.yml` as generated today — Gate 3 does not change the compose file's port bindings, only documents and reinforces them.

## TLS behavior

Caddy automates TLS certificate issuance and renewal via Let's Encrypt (or ZeroSSL fallback) for any domain listed in the Caddyfile, provided:

1. The domain's DNS A record already points to the VPS IP (DNS must resolve before Caddy can complete the ACME HTTP-01 or TLS-ALPN-01 challenge).
2. Ports 80 and 443 are open on the VPS firewall (see `docs/VPS-BOOTSTRAP-RUNBOOK.md` Step 6).
3. The `email` directive in the Caddyfile's global block is set to a real operator email for renewal notices — replace `admin@example.org` before go-live.

No manual certbot step is required. Caddy renews certificates automatically before expiry. If a route is internal-only (bound to `127.0.0.1` or accessed only via SSH tunnel), it does not need — and should not request — a public TLS certificate.

## Where `Caddyfile.managed` comes from

`handoff/<tenant>/managed/Caddyfile.managed` is generated by `missionctl bundle up <tenant> --dry-run` from a template. The demo tenant's generated file (`handoff/demo-pnw/managed/Caddyfile.managed`) currently routes:

```
api.demo-pnw.org        → mission-api:4000
demo-pnw.org             → site:3000
demo-pnw.org/workspace/* → open-webui:8080
demo-pnw.org/observability/* → langfuse-web:3000
```

This demo file uses path-based routing for Open WebUI and Langfuse under the public site domain, which is **not** the recommended pattern for a real client deployment — those services should move to protected subdomains or be accessed only via SSH tunnel, per the domain model above. Treat `demo-pnw.org` as a placeholder pattern to replace, not a template to deploy as-is.

## How to replace demo-pnw.org placeholders

1. Run `missionctl tenant create <slug> --org "<Org Name>" --domain "https://os.<client-domain>" --api "https://api.<client-domain>"` with the real client domain.
2. Run `missionctl bundle up <slug> --dry-run` to regenerate `Caddyfile.managed` with the tenant's configured domains.
3. Manually review the generated file — confirm no `demo-pnw.org` or other placeholder string remains.
4. Move the Open WebUI and Langfuse routes off the public site domain: either remove them from the public Caddyfile entirely (access via SSH tunnel only) or place them on a protected subdomain guarded by `basic_auth` / forward-auth.
5. Set the `email` directive in the Caddyfile's global block to a real operator email.
6. Do not commit the client-specific `Caddyfile.managed` to this repository — it is generated into `handoff/<slug>/managed/`, which is a per-tenant runtime artifact. `docs/SECURITY-CHECKLIST.md` governs which handoff files may be tracked.

## How to validate Caddy config before reload

```bash
# LIVE COMMAND — DO NOT RUN UNTIL HUMAN APPROVES
ssh deploy@<HOSTINGER_VPS_IP> "cd /opt/mission-os/handoff/<slug>/managed && docker run --rm -v \$(pwd)/Caddyfile.managed:/etc/caddy/Caddyfile:ro caddy:2-alpine caddy validate --config /etc/caddy/Caddyfile"
```

This validates Caddyfile syntax without starting the reverse proxy or touching live traffic. Run this after every edit to `Caddyfile.managed` and before any `docker compose up` or `docker exec caddy caddy reload`.

To reload a running Caddy container without downtime after a validated config change:

```bash
# LIVE COMMAND — DO NOT RUN UNTIL HUMAN APPROVES
ssh deploy@<HOSTINGER_VPS_IP> "cd /opt/mission-os/handoff/<slug>/managed && docker compose exec caddy caddy reload --config /etc/caddy/Caddyfile"
```
