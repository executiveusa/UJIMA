# Hostinger Phase 9 Staging — Mission OS

**Audience:** Architect, operator, client stakeholders
**Purpose:** Define the target staging topology for a client-owned Hostinger VPS deployment of Mission OS + Hermes + LiteLLM + Langfuse + Open WebUI
**Status:** Specification and runbook only. No live deployment has occurred under Gate 3.

---

## Scope of this gate

Gate 3 produces the plan, not the deployment. Nothing in this document set:

- SSHes into a VPS
- Runs Docker on a remote server
- Changes DNS
- Changes Vercel configuration
- Generates or commits real secrets
- Calls a live external service
- Exposes Open WebUI, Langfuse, LiteLLM, or Hermes publicly

Live deployment happens after a human provides a VPS IP, an SSH method, a staging domain, and explicit approval. See `docs/PHASE-9-GO-LIVE-GATES.md` for the gate sequence that must pass before any live command runs.

## Services

| Service | Role | Public exposure |
|---|---|---|
| Caddy | Reverse proxy, TLS termination, routing | Public (ports 80/443) |
| Mission OS web app (`site`) | Ops dashboard + public site (Next.js) | Public via Caddy |
| Mission API (`mission-api`) | Operator API, Agent Service API, tenant data | Public via Caddy (API routes only) |
| Postgres | Production database | Internal only — no public port |
| Hermes runtime | Managed agent worker | Internal/protected only — `127.0.0.1:8765` |
| LiteLLM | Model gateway/proxy | Internal only — no public port |
| Langfuse | Observability/trace store | Internal/protected only |
| Open WebUI | Staff-facing chat interface | Internal/protected only |
| ICM workspace volume | Tenant ICM stage contracts and outputs | Not exposed — volume mount |
| Tenant data volume | `mission-data/<tenant>/` file-backed state | Not exposed — volume mount |
| Backup volume | Local backup archives | Not exposed — volume mount |

This topology matches the existing `deploy/docker-compose.yml` (v0.5 base) and `handoff/<tenant>/managed/docker-compose.managed.yml` (v0.6 managed bundle) already generated by `missionctl bundle up`. Gate 3 does not introduce new services — it documents how to run the existing generated bundle safely on a real VPS.

## Domain model

Use placeholders only. No real domains appear in this document set unless a human provides them later.

```
os.<client-domain>        candidate for public DNS — Mission OS web app
api.<client-domain>       candidate for public DNS — Mission API
agents.<client-domain>    protected/internal — Hermes
traces.<client-domain>    protected/internal — Langfuse
models.<client-domain>    protected/internal — LiteLLM
```

**Only `os.<client-domain>` and `api.<client-domain>` are candidates for public DNS.** `agents`, `traces`, and `models` must remain protected unless an explicit access-control layer (VPN, SSH tunnel, IP allowlist, or authenticated reverse-proxy rule) is configured. See `docs/CADDY-DOMAIN-MAP.md` for the routing rules that enforce this.

## What Gate 3 does not do

| Not done in Gate 3 | Reason |
|---|---|
| Live VPS provisioning | Requires human-provided VPS IP and SSH access |
| DNS record creation | Requires human-owned domain and DNS access |
| TLS certificate issuance | Requires live DNS resolution first |
| `docker compose up -d` on a real host | Gated behind human approval — see Gate N in `docs/PHASE-9-GO-LIVE-GATES.md` |
| Postgres cutover from file-backed state | Requires a completed migration/restore drill — see `docs/POSTGRES-MIGRATION-RUNBOOK.md` |
| Live Hermes, LiteLLM, Langfuse, or Open WebUI execution | Deferred to Phase 9B per `docs/HERMES-AGENT-SERVICE-API.md` and `docs/SOVEREIGN-AI-CLIENT-STACK.md` |

## What Gate 3 provides

- A concrete, reviewable staging plan an operator can follow on a real Hostinger VPS without guesswork.
- A secret inventory with generation, storage, and rotation rules — no real values committed anywhere.
- A domain map that keeps internal services (Hermes, Langfuse, LiteLLM) off the public internet by default.
- A go-live gate checklist (`docs/PHASE-9-GO-LIVE-GATES.md`) with owner, evidence, and rollback requirements per gate, so live deployment happens in reviewable, reversible steps.

Gate 3 is complete when the docs, tests, and smoke checks below exist and pass — not when a VPS is running Mission OS.
