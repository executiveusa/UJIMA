# Sovereign AI Client Stack — Mission OS v0.6

## What "sovereign" means

A sovereign AI deployment means the client owns and controls:

- The VPS or server the software runs on
- The source code (MIT/open license — no lock-in)
- The database and all backups
- The API keys and credentials (generated fresh at deploy time)
- The agent runtime (Hermes runs on their infrastructure)
- The ICM workspace and all tenant data

No data is sent to a third-party SaaS platform without the client's explicit configuration. No vendor can revoke access. No per-seat pricing surprises. No forced cloud dependency.

## Architecture overview

```
Client VPS
├── Mission OS (Node.js apps + services)
│   ├── apps/site          — Ops dashboard (Next.js)
│   ├── services/mission-api — REST API (Express)
│   └── packages/core      — Core modules (file-backed, no cloud dep)
├── Hermes agent runtime   — Managed Pi-compatible agent worker
├── LiteLLM gateway        — Model proxy (routes to any LLM provider)
├── Langfuse               — Observability (self-hosted or cloud)
├── Open WebUI             — Staff-facing chat interface
├── PostgreSQL             — Production database (local)
└── Backup storage         — Local + optional offsite
```

All components run on the client's server. The client controls every credential. Nothing is phoned home to a Mission OS SaaS endpoint.

## Client owns the VPS

Mission OS is installed on client-controlled infrastructure. The deployment process:

1. Client provisions a VPS (Hostinger, DigitalOcean, Linode, or any Linux host)
2. Operator runs `missionctl bundle up <tenantId>` to generate the managed env bundle
3. Operator runs the VPS deployment plan (see `docs/DEPLOY-HOSTINGER-VPS.md`)
4. Client receives all generated credentials and stores them securely

After deployment, the client can operate the system without any ongoing relationship with Mission OS. All code is on their server. All data is in their database.

## Client owns the database

PostgreSQL runs on the client's VPS. Backups are stored locally by default and can be configured for offsite storage via `missionctl bundle backup`.

Migration SQL is in `db/migrations/`. The client can apply or revert migrations independently.

Mission OS does not have access to the client's database. There is no shared cloud database.

## Client owns the AI agent

Hermes runs on the client's VPS as a managed worker. The Hermes agent configuration is generated by:

```bash
node missionctl/missionctl.mjs hermes provision <tenantId>
```

This produces:
- `handoff/<tenantId>/managed/hermes/env` — agent environment variables
- `handoff/<tenantId>/managed/hermes/SOUL.md` — agent identity
- `handoff/<tenantId>/managed/hermes/skills/*.md` — skill definitions

These files are gitignored and never leave the client's environment. The client owns the agent's identity, skills, and configuration.

## Single-tenant by default

Each VPS hosts one client organization by default. This prevents data co-mingling and simplifies the security model.

Multi-tenant hosting (multiple orgs on one VPS) is technically possible using the tenant slug isolation (`mission-data/<tenantId>/`), but is not the default or recommended configuration for production deployments.

## No forced SaaS subscription

Mission OS is not a SaaS subscription product. Clients:

- Pay once for the deployment bundle and initial setup
- Own the software indefinitely
- Can receive optional ongoing support (see below)
- Can operate independently without a support contract

There is no recurring per-seat fee for the core software. Optional managed support is a separate arrangement.

## Optional managed support

Clients can choose optional managed agent support, which means:

- Mission OS operator monitors and maintains the Hermes agent pack
- Operator applies updates when the client requests
- Operator assists with ICM workspace configuration
- Operator reviews agent outputs and approvals before they reach staff

This is an opt-in service layer, not a dependency. Clients who stop the support contract retain full access to their software and data.

See `docs/MANAGED-AGENTS-AS-A-SERVICE.md` for the managed support offer.

## How the Hermes agent service fits in

The Agent Service API (`/api/agent`) is the interface between the Hermes worker and Mission OS. Because both run on the same VPS, the network call is local (no internet required):

```
Hermes container → http://localhost:4000/api/agent/context/:tenantId
Hermes container → http://localhost:4000/api/agent/runs
Mission OS → stores events, artifacts, approvals in mission-data/<tenantId>/
```

No model outputs leave the VPS unless the client configures an external LangFuse endpoint or an LLM provider API. The LiteLLM gateway can be configured to use local models (Ollama) for fully offline operation.

## LLM provider choice

Mission OS does not lock the client to a specific LLM provider. The LiteLLM gateway supports:

- OpenAI / Azure OpenAI
- Anthropic Claude
- Google Gemini
- Ollama (local, fully offline)
- Any OpenAI-compatible endpoint

The client configures their preferred provider in the LiteLLM environment. They can switch providers without changing Mission OS code.

## What Mission OS does not do

| Thing | Why not |
|---|---|
| Store client data on Mission OS servers | All data is on the client's VPS |
| Require internet access for core operations | File-backed modules work offline |
| Charge per API call | Client pays their own LLM provider |
| Access client's VPS without permission | No remote access capability built in |
| Make live agent decisions without human gates | Approval gates are mandatory |
| Guarantee grant funding, legal compliance, or outcomes | Out of scope — see `docs/LEGAL-SAFETY-NOTES.md` |

## Summary of ownership

| Resource | Owner |
|---|---|
| VPS hardware | Client (or client's hosting provider) |
| Domain and DNS | Client |
| PostgreSQL database | Client |
| All `mission-data/` files | Client |
| Operator keys | Client (generated by missionctl, never shared) |
| Hermes agent config | Client |
| Source code | Client (MIT license) |
| ICM workspaces | Client |
| LLM provider credentials | Client |
| Backup files | Client |

Mission OS is the software. The client is the operator.
